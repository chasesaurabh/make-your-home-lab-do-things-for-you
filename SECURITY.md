# Security policy

This synthetic teaching application has no operational support guarantee. Its writable target is one disposable setting and two bundled strings. Use no personal data, production logs, real runbooks or existing application data as fixtures.

Tools have no model-controlled commands, paths, SQL or URLs. Models cannot grant approvals or invoke effects. Approvals bind exact proposal, job, target/version, evidence, policy and expiry. Operator names are audit labels, not authentication. Anyone controlling the OS account or database can bypass the teaching application's rules. Loopback does not authenticate other local users; keep the read-only board off the LAN.

Target receipts are separate from job state. Unknown writes never trigger blind retries. Missing receipts, partial artifacts or failed verification require inspection. Offline snapshots require all workers/board to stop and do not establish consistency against concurrent writers. The lab promises no real-time deadlines, hostile-local-user isolation, physical storage guarantees or exactly-once external effects.

Report ordinary defects with synthetic reproductions in repository issues. For vulnerabilities, use GitHub private vulnerability reporting if offered in the Security tab. If unavailable, open only a non-sensitive coordination issue without exploit details or secrets while arranging a private channel. No paid security support is promised.

Before every push/release, inspect the staged list, scan secrets/private data, review dependency versions/licenses/advisories, run meaningful boundary/failure tests, and reproduce installation. Refresh checks after changes. A pattern scan or successful model run is not security certification. Never add credentials, personal information, private logs, weights, manuscript or production assets.
